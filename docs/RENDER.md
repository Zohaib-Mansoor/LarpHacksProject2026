# Deploy PlayCall on Render

Deploy the frontend and backend together as **one Docker Web Service**, plus one
PostgreSQL database. The server already serves the frontend at `/` and its API at
`/api/`. Every player uses the same public HTTPS address, with separate session
cookies. No separate Static Site, frontend API URL, or cross-origin cookie setup
is needed for this version.

## 1. Create your Render account

Go to https://dashboard.render.com/register and complete signup yourself. Connect
your GitHub account and grant Render access to `Zohaib-Mansoor/LarpHacksProject2026`.
If the repository is not listed, review the GitHub installation's repository access.
Render's [first-deploy guide](https://render.com/docs/your-first-deploy) covers signup
and Git provider linking.

## 2. Put the latest local changes on GitHub

The Gemini and Render setup changes are local until committed and pushed. Review
them, then commit/push them on your chosen deployment branch. Do not commit
`backend/.env`; the Gemini key goes into Render's private environment settings.

The Blueprint uses the branch you select in Render. Select the branch containing
the merged frontend, backend, Gemini integration, and this `render.yaml` file.
The existing integrated branch is `akshi/larphacks-project-2026`.

## 3. Deploy the Blueprint

1. In Render, select **New → Blueprint**.
2. Connect the repository and select the deployment branch from step 2.
3. Keep the Blueprint path as `render.yaml`.
4. Enter `GEMINI_API_KEY` when prompted. Use the real key only in that private field.
5. Review the resources: `playcall` Web Service and `playcall-db` PostgreSQL.
6. Confirm the Free plans, then deploy.

The Blueprint builds from the repository root with `backend/Dockerfile`. It copies
the frontend into the same image, generates a session secret, connects the managed
database over Render's internal network, applies only `backend/drizzle` migrations,
then starts the server. Health checks use `/ready`.

Auth and trusted origins default to Render's actual `RENDER_EXTERNAL_URL`. If you
later add a custom domain, explicitly set `BETTER_AUTH_URL` and `CLIENT_ORIGINS` to
that exact HTTPS origin. No trailing slash. The public URL is generated by Render;
do not assume the service name alone determines it.

The Blueprint is based on Render's [official YAML reference](https://render.com/docs/blueprint-spec)
and [Docker deployment instructions](https://render.com/docs/docker).

## 4. Verify the public app with two people

- Open the Web Service's public URL and confirm `/ready` returns `{"status":"ready"}`.
- You create a private room and send its complete invite link to Akshit.
- Akshit opens it on his own device or in an independent browser profile and joins.
- Both players ready up, read their private briefs, and negotiate.
- Publish terms, revise once to confirm acceptances reset, then both confirm the
  same revision. Check scores and reload to confirm persistence.

Use two separate browser profiles if testing on one computer. Two ordinary tabs
in the same profile share cookies and therefore represent the same player.

The current integrated mode uses text and polling. Gemini can generate situations.
Voice, speech-to-text, automatic conversation grading, and random matchmaking are
not enabled by this deployment. Private invites support multi-user testing now.

## Manual setup alternative

If you do not use the Blueprint, create Postgres and a Docker Web Service in the
same region with these settings:

| Setting              | Value                                                    |
| -------------------- | -------------------------------------------------------- |
| Repository           | Zohaib-Mansoor/LarpHacksProject2026                      |
| Branch               | Your integrated deployment branch                        |
| Root directory       | Leave empty                                              |
| Dockerfile path      | `backend/Dockerfile`                                     |
| Docker build context | Repository root                                          |
| Docker command       | `sh ./start-render.sh`                                   |
| Health check         | `/ready`                                                 |
| NODE_ENV             | `production`                                             |
| HOST                 | `0.0.0.0`                                                |
| PORT                 | `10000`                                                  |
| DEMO_MODE            | `true`                                                   |
| DATABASE_URL         | Postgres internal connection URL                         |
| BETTER_AUTH_SECRET   | Generate a fresh random secret of at least 32 characters |
| AI_PROVIDER          | `gemini`                                                 |
| GEMINI_MODEL         | `gemini-3.1-flash-lite`                                  |
| GEMINI_API_KEY       | Your private provider key                                |

For the manual route, Render still supplies its public URL automatically. Set
explicit auth/client origins only for a custom domain or deliberate override.
The database must be new and dedicated to the integrated app; do not apply the
legacy root migrations to it.

## Free-plan limits and updates

Render's Free web service sleeps after 15 minutes without inbound traffic; its
first request afterward can take about a minute. Free Postgres expires 30 days
after creation. These tiers are for a short test deployment. Upgrade if you need
continuous availability or long-lived data. Gemini usage has its own provider limits
and charges. See [Render's Free plan documentation](https://render.com/docs/free).

Automatic application deploys are initially off. After pushing a tested update,
choose **Manual Deploy → Deploy latest commit**. The startup script applies pending
migrations before starting the single test instance. For paid/scaled deployment,
move migrations into Render's pre-deploy command and run the server alone at startup.

Docker could not run on the development machine, so the actual image still needs
its first build on Render. The backend and live database flows were verified
locally; a successful public deployment has not yet been performed.
